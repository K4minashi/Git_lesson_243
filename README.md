
# 🚀 Добро пожаловать на урок по Git и удалённым репозиториям!
##  Начало работы

1. **Зарегистрируйся и создай Токен (Personal Access Token):**
   - Нажми на свой аватар справа сверху → **Settings** (Настройки).
   - Прокрути самый низ левой боковой панели и нажми **Developer settings**.
   - Слева выбери **Personal access tokens** → **Tokens (classic)**.
   - Нажми **Generate new token** → **Generate new token (classic)**.
   - В поле *Note* напиши `course`, выбери срок действия (например, 30 дней).
   - **Обязательно** поставь галочку напротив scope **`repo`** (полный доступ к репозиториям).
   - Нажми кнопку **Generate token** внизу страницы.
   - ⚠️ **Скопируй токен** (начинается с `ghp_...`) и сохрани его в надёжное место! GitHub покажет его только один раз.

2. **Отметься в задаче:**
   - Перейди во вкладку **Issues** (Задачи) в этом репозитории.
   - Открой задачу с названием **«Добавление в репозиторий»**.
   - Напиши в комментариях только свой **никнейм** (например: `ivan_dev`).
   - *Преподаватель увидит твой ник и добавит тебя в коллабораторы (Collaborators) этого репозитория.*

3. **Склонируй репозиторий и настрой Git:**
   - Нажми зелёную кнопку **<> Code**, выбери вкладку **HTTPS** и скопируй ссылку.
   - Вставь свой ТОКЕН в начало ссылки (сразу после `https://`) и выполни в терминале:
   ```bash
   # Скачиваем репозиторий на компьютер. Токен в ссылке заменяет пароль.
   git clone https://<ТВОЙ_ТОКЕН>@github.com/ЛОГИН_УЧИТЕЛЯ/НАЗВАНИЕ_РЕПО.git
   
   # Переходим в папку скачанного репозитория
   cd НАЗВАНИЕ_РЕПО
   
   # Настраиваем имя автора коммитов (будет видно в истории)
   git config --global user.name "Твоё Имя"
   
   # Настраиваем email автора (--global сохраняет настройку для всех репозиториев на этом ПК)
   git config --global user.email "твоя@почта.com"
   ```

## ⚠️ Золотое правило работы в этом репозитории

Чтобы никогда не создавать конфликтов с другими студентами, мы работаем **только в своих личных ветках**.

**Твой алгоритм на весь курс:**
1. Сначала создай свою **базовую личную ветку** от главной:
   ```bash
   # Переключаемся на главную ветку и получаем её свежую версию с сервера
   git checkout main
   
   # Создаём новую ветку feature/<твой_ник> и сразу переключаемся на неё
   # Флаг -b означает "create branch" (создать ветку)
   git checkout -b feature/<твой_ник>
   ```
2. Все задания, **кроме первого** выполняй в **новых ветках, созданных на основе твоей базовой ветки**:
   ```bash
   # Сначала возвращаемся в свою базовую ветку
   git checkout feature/<твой_ник>
   
   # Создаём от неё новую ветку для конкретного задания
   git checkout -b feature/<твой_ник>/task-X
   ```

## 🎯 Задания

### Задание: Создание профиля разработчика
**Цель:** Создать первую ветку, добавить файл и отправить его на сервер.

1. Убедись, что ты находишься в своей базовой ветке:
   ```bash
   
   # Переключаемся на свою базовую ветку (если ещё не на ней)
   git checkout feature/<твой_ник>
   ```

2. Создай файл `contributors/<твой_ник>.md` и заполни его по шаблону:
   ```markdown
   # Профиль: [Твоё Имя]
   
   - **Никнейм:** <твой_ник>
   - **Интересы:** [Напиши, что тебе интересно в IT]
   - **Цель:** [Чему хочешь научиться]
   ```

3. Сохрани изменения, сделай коммит и отправь ветку:
   ```bash
   # git add добавляет файл в "индекс" (подготавливает к коммиту)
   # Точка (.) означает "добавить все изменённые файлы"
   git add contributors/<твой_ник>.md
   
   # git commit создаёт "снимок" изменений в индексе
   # Флаг -m позволяет сразу написать сообщение коммита в кавычках
   git commit -m "Добавил профиль разработчика"
   
   # git push отправляет локальную ветку на удалённый сервер (origin)
   # Флаг -u (или --set-upstream) связывает локальную ветку с удалённой,
   # чтобы в будущем можно было писать просто "git push" без указания ветки
   git push -u origin feature/<твой_ник>
   ```

4. Создай **Pull Request** в GitHub, чтобы преподаватель проверил и слил твою базовую ветку.

### Задание: Добавление идеи проекта
**Цель:** Научиться создавать вложенные ветки от своей базовой ветки.

1. Вернись в свою базовую ветку и создай от неё новую для этого задания:
   ```bash
   # Возвращаемся в базовую ветку
   git checkout feature/<твой_ник>
   
   # Создаём новую ветку task-2 ОТ текущей (feature/<твой_ник>)
   git checkout -b feature/<твой_ник>/task-2
   ```

2. Создай папку `ideas` (если её нет) и файл `ideas/<твой_ник>.md`. Напиши в нём идею для любого пет-проекта.

3. Отправь изменения:
   ```bash
   # Добавляем файл в индекс
   git add ideas/<твой_ник>.md
   
   # Создаём коммит с понятным сообщением
   git commit -m "Добавил идею проекта"
   
   # Отправляем ветку на сервер. Флаг -u запоминает связь с удалённой веткой
   git push -u origin feature/<твой_ник>/task-2
   ```

4. Создай **Pull Request** для этой ветки.

### Задание: Работа с черновиками (Stash)
**Цель:** Научиться временно прятать изменения, если нужно срочно переключиться.

1. Создай новую ветку от своей базовой:
   ```bash
   git checkout feature/<твой_ник>
   git checkout -b feature/<твой_ник>/task-3
   ```

2. Открой свой профиль `contributors/<твой_ник>.md` в редакторе `nano` и начни писать туда длинный текст, но **не делай коммит**.

3. Представь, что тебе срочно нужно переключиться. "Заморозь" изменения:
   ```bash
   # git stash сохраняет все незакоммиченные изменения во временное хранилище
   # и возвращает рабочую директорию в чистое состояние (как после последнего коммита)
   # Сообщение в кавычках поможет потом понять, что именно ты спрятал
   git stash save "Начатый текст профиля"
   ```

4. Проверь, что файл стал чистым:
   ```bash
   # git status показывает текущее состояние репозитория
   # Должно быть написано "nothing to commit, working tree clean"
   git status
   ```

5. Теперь "разморозь" изменения обратно:
   ```bash
   # git stash pop достаёт последний спрятанный набор изменений
   # и удаляет его из списка stash (в отличие от git stash apply, который оставляет копию)
   git stash pop
   ```

6. Заверши работу: сохрани файл, сделай коммит и отправь ветку на сервер. Создай Pull Request.

### Задание: Откат изменений (Reset)
**Цель:** Научиться исправлять ошибки и отменять коммиты **до того, как они отправлены на сервер**.

1. Создай новую ветку:
   ```bash
   git checkout feature/<твой_ник>
   git checkout -b feature/<твой_ник>/task-4
   ```

2. Создай файл `temp.txt`, добавь его и сделай коммит:
   ```bash
   # Создаём файл с текстом (перенаправление вывода в файл)
   echo "Тестовый текст" > temp.txt
   
   # Добавляем файл в индекс
   git add temp.txt
   
   # Делаем коммит
   git commit -m "Добавил временный файл"
   ```

3. Осознай, что файл не нужен. Отмени последний коммит, но оставь файл в рабочей директории:
   ```bash
   # git reset --soft HEAD~1 отменяет последний коммит,
   # но оставляет изменения в индексе (готовыми к новому коммиту)
   # --soft = "мягкий" режим: не трогает файлы, только перемещает указатель ветки
   # HEAD~1 = "предыдущий коммит относительно текущего" (HEAD — это указатель на текущий коммит)
   git reset --soft HEAD~1
   ```

4. Теперь убери файл из индекса и удали его полностью:
   ```bash
   # git restore --staged убирает файл из индекса (отменяет git add),
   # но оставляет сам файл на диске
   git restore --staged temp.txt
   
   # rm — стандартная команда Linux для удаления файла
   rm temp.txt
   ```

5. Сделай коммит с сообщением "Очистил репозиторий от мусора" и отправь ветку. Создай Pull Request.

### Задание: Откат запушенных изменений (Revert) ⚠️
**Цель:** Научиться безопасно отменять изменения, которые **уже отправлены на сервер**. Это один из самых важных навыков в командной работе!

> **Важно:** Никогда не используй `git reset --hard` для отката запушенных изменений, если с этой веткой работают другие люди. Это переписывает историю и ломает работу команды. Вместо этого используй `git revert`.

1. Создай новую ветку:
   ```bash
   git checkout feature/<твой_ник>
   git checkout -b feature/<твой_ник>/task-5
   ```

2. Создай файл `mistake.txt`, добавь его, сделай коммит и **сразу запушь**:
   ```bash
   # Создаём "ошибочный" файл
   echo "Этот файл был добавлен по ошибке" > mistake.txt
   git add mistake.txt
   git commit -m "Добавил mistake.txt (позже поймём, что зря)"
   
   # Отправляем на сервер — теперь этот коммит "публичный"
   git push -u origin feature/<твой_ник>/task-5
   ```

3. Поняли, что файл лишний. Смотрим историю коммитов, чтобы найти его хеш:
   ```bash
   # git log показывает историю коммитов
   # --oneline — компактный формат (одна строка на коммит)
   # -n 3 — показать только последние 3 коммита
   git log --oneline -n 3
   ```
   Ты увидишь что-то вроде:
   ```
   a1b2c3d Добавил mistake.txt (позже поймём, что зря)
   e4f5g6h Добавил идею проекта
   i7j8k9l Добавил профиль разработчика
   ```
   Скопируй хеш первого коммита (например, `a1b2c3d`).

4. **Безопасный откат через `git revert`:**
   ```bash
   # git revert создаёт НОВЫЙ коммит, который отменяет изменения указанного коммита
   # История не переписывается — это безопасно для командной работы!
   # Флаг --no-edit автоматически использует стандартное сообщение коммита
   # (иначе откроется редактор, где нужно будет подтвердить сообщение)
   git revert a1b2c3d --no-edit
   ```

5. Проверь результат:
   ```bash
   # Файл mistake.txt должен исчезнуть из рабочей директории
   ls
   
   # А в истории появится новый коммит "Revert 'Добавил mistake.txt...'"
   git log --oneline -n 3
   ```

6. Отправь откат на сервер:
   ```bash
   # Обычный push — никаких force не нужно, история чистая
   git push origin feature/<твой_ник>/task-5
   ```

7. Создай Pull Request. В описании напиши: *"Отменил ошибочный коммит через git revert"*.

---

####  Альтернатива: Опасный откат через `git reset --hard` + `force push`
*Используй только в личных ветках, где никто кроме тебя не работает!*

```bash
# git reset --hard HEAD~1 полностью отменяет последний коммит
# --hard = "жёсткий" режим: удаляет и коммит, и изменения в файлах
# HEAD~1 = откатиться на один коммит назад
git reset --hard HEAD~1

# ⚠️ ВНИМАНИЕ: Теперь локальная история "отстала" от удалённой.
# Обычный git push будет отклонён GitHub'ом.
# Нужно использовать --force (или -f), чтобы принудительно перезаписать удалённую ветку:
git push origin feature/<твой_ник>/task-5 --force

# Более безопасный вариант --force-with-lease:
# Он проверит, не изменил ли кто-то удалённую ветку пока ты работал,
# и откажется делать force push, если изменения есть.
git push origin feature/<твой_ник>/task-5 --force-with-lease
```

> **Правило большого пальца:** В личных ветках (`feature/твой_ник/...`) можно использовать `--force`. В общих ветках (`main`, `develop`) — **никогда**, только `git revert`.

### Задание: Теги и версии (Tags)
**Цель:** Научиться помечать важные этапы работы.

1. Убедись, что ты в своей базовой ветке:
   ```bash
   git checkout feature/<твой_ник>
   ```

2. Создай аннотированный тег для текущей версии твоей ветки:
   ```bash
   # git tag -a создаёт аннотированный тег (с автором, датой и сообщением)
   # -a = "annotated" (аннотированный, в отличие от лёгкого тега без метаданных)
   # v1.0 — имя тега (обычно используют семантическое версионирование: v1.0, v2.1.3)
   # -m — сообщение, которое будет храниться вместе с тегом
   git tag -a v1.0 -m "Первая стабильная версия профиля"
   ```

3. Посмотри список своих тегов:
   ```bash
   # git tag без аргументов выводит все теги в репозитории
   git tag
   ```

4. Посмотри подробную информацию о теге:
   ```bash
   # git show показывает полную информацию о теге: кто создал, когда, какое сообщение,
   # а также какие изменения были в коммите, на который указывает тег
   git show v1.0
   ```

5. Отправь тег на удалённый сервер (обычный `git push` теги не отправляет!):
   ```bash
   # Отправляем конкретный тег на сервер
   git push origin v1.0
   
   # Или можно отправить все локальные теги одной командой:
   # git push origin --tags
   ```

6. Создай новую **Issue** (Задачу) с заголовком: `Тег v1.0 успешно создан` и кратко опиши в теле задачи, что ты сделал.

##  Шпаргалка полезных команд

### Просмотр состояния
```bash
# Показать статус рабочей директории: какие файлы изменены, добавлены, не отслеживаются
git status

# История коммитов в компактном виде с графом веток
# --oneline — одна строка на коммит (хеш + сообщение)
# --graph — ASCII-граф веток и слияний
git log --oneline --graph

# Список всех веток: локальных и удалённых
# -a = --all (показать все ветки)
git branch -a

# Список удалённых репозиториев и их URL
# -v = --verbose (показать URL рядом с именем)
git remote -v
```

### Работа с ветками
```bash
# Создать новую ветку и сразу переключиться на неё
# -b = --branch (создать ветку)
git checkout -b <имя_ветки>

# Просто переключиться на существующую ветку
git checkout <имя_ветки>

# Слить указанную ветку в текущую
git merge <имя_ветки>
```

### Отмена изменений (локальных, до push)
```bash
# Отменить изменения в файле (вернуть к состоянию последнего коммита)
git restore <файл>

# Убрать файл из индекса (отменить git add), но оставить изменения в файле
git restore --staged <файл>

# Отменить последний коммит, но оставить изменения в индексе (готовыми к новому коммиту)
# --soft = мягкий режим, не трогает файлы
# HEAD~1 = на один коммит назад
git reset --soft HEAD~1

# Отменить последний коммит и полностью удалить все изменения в файлах
# --hard = жёсткий режим, файлы возвращаются к состоянию коммита
# ⚠️ ОПАСНО: изменения будут потеряны безвозвратно!
git reset --hard HEAD~1
```

### Отмена изменений (после push)
```bash
# Безопасный откат запушенного коммита: создаёт НОВЫЙ коммит, отменяющий изменения
# История не переписывается — безопасно для командной работы
# --no-edit — не открывать редактор для сообщения коммита
git revert <хеш_коммита> --no-edit

# Опасный откат: переписывает историю и требует force push
# Использовать ТОЛЬКО в личных ветках!
git reset --hard HEAD~1
git push origin <ветка> --force

# Более безопасная версия force push (проверяет, не изменил ли кто-то ветку)
git push origin <ветка> --force-with-lease
```

### Работа с временным хранилищем (Stash)
```bash
# Сохранить текущие изменения во временное хранилище и очистить рабочую директорию
git stash save "описание изменений"

# Посмотреть список всех спрятанных изменений
git stash list

# Достать последний stash и удалить его из списка
git stash pop

# Достать stash, но оставить его копию в списке (не удалять)
git stash apply
```

### Теги
```bash
# Создать аннотированный тег с сообщением
git tag -a <имя_тега> -m "сообщение"

# Посмотреть все теги
git tag

# Отправить конкретный тег на сервер
git push origin <имя_тега>

# Отправить все локальные теги на сервер
git push origin --tags
```

### Задание: Code Review
**Цель:** Научиться читать чужой код, находить ошибки и давать конструктивную обратную связь. Это одна из ключевых обязанностей любого разработчика в компании!

> **Легенда:** Ты — опытный разработчик, к которому на проверку пришёл Pull Request от коллеги. Твоя задача — внимательно изучить изменения, найти возможные проблемы и оставить комментарии.

1. **Найди открытый Pull Request другого студента** во вкладке **Pull Requests** репозитория. Выбери тот, где ещё нет комментариев от преподавателя.

2. **Изучи изменения (Diff):**
   - Открой вкладку **Files changed** в Pull Request.
   - GitHub покажет тебе все изменения: красные строки — удалены, зелёные — добавлены.
   - Внимательно прочитай код/текст. Ищи: опечатки, странные формулировки, отсутствие информации, нарушение формата.

3. **Оставь комментарий к конкретной строке:**
   - Наведи курсор на номер строки — слева появится синий значок `+`.
   - Нажми на него и напиши свой комментарий (например: *"Здесь лучше указать конкретный язык программирования"* или *"Опечатка в слове 'программирование'"*).
   - Нажми **Start a review**.

4. **Заверши ревью:**
   - Нажми кнопку **Review changes** справа сверху.
   - Выбери тип ревью:
     - **Comment** — просто оставить комментарий (без одобрения).
     - **Approve** — approve, всё хорошо, можно мержить.
     - **Request changes** — есть замечания, нужно исправить.
   - Напиши общее резюме в поле комментария (например: *"В целом хорошо, но исправь опечатку в строке 3"*).
   - Нажми **Submit review**.

5. **Создай Issue** с заголовком: `Провёл Code Review для PR #<номер>` и опиши, что ты заметил.

### Задание: Баг-репорт и исправление 
**Цель:** Научиться находить ошибки в чужом коде, правильно оформлять баг-репорты и чинить их. Это основа работы QA-инженера и разработчика.

> **Легенда:** Преподаватель создал в репозитории "секретную" ветку `buggy/feature` с намеренными ошибками. Ты — тестировщик, который нашёл баг, и разработчик, который его чинит.

1. **Получи "проблемную" ветку преподавателя:**
   ```bash
   # Обновляем список всех удалённых веток с сервера
   # git fetch скачивает изменения, но НЕ сливает их в твою ветку
   git fetch origin
   
   # Посмотреть все удалённые ветки, включая buggy/feature
   git branch -r
   ```

2. **Создай локальную копию ветки преподавателя для изучения:**
   ```bash
   # Создаём локальную ветку на основе удалённой
   # origin/buggy/feature — это ссылка на ветку на сервере
   git checkout -b study/buggy origin/buggy/feature
   ```

3. **Изучи файлы в ветке и найди "баги"** (опечатки, неработающие ссылки, странный формат). Открой файлы через `nano` или в VS Code.

4. **Создай Issue с баг-репортом:**
   - Перейди во вкладку **Issues** → **New issue**.
   - Заголовок: `Баг: [краткое описание проблемы]`.
   - В теле задачи используй шаблон:
     ```markdown
     ## Описание бага
     [Что не так?]
     
     ## Где находится
     Файл: [путь к файлу]
     Строка: [номер строки, если возможно]
     
     ## Ожидаемое поведение
     [Как должно быть?]
     
     ## Фактическое поведение
     [Как сейчас?]
     ```

5. **Создай ветку для исправления и почини баг:**
   ```bash
   # Возвращаемся в свою базовую ветку
   git checkout feature/<твой_ник>
   
   # Создаём ветку для фикса
   git checkout -b feature/<твой_ник>/bugfix-1
   ```

6. **Внеси исправления в файлы** (через `nano`), затем:
   ```bash
   git add .
   git commit -m "Исправил баг: [краткое описание]. Closes #<номер_Issue>"
   git push -u origin feature/<твой_ник>/bugfix-1
   ```

7. Создай **Pull Request** и в описании укажи: *"Исправляет #<номер_Issue>"*.

### 📚 Дополнительные команды: Работа с чужими ветками

```bash
# Получить список всех веток на удалённом сервере (без скачивания)
# origin/ — префикс, означающий "ветка на сервере origin"
git branch -r

# Скачать все изменения с сервера, но НЕ сливать их
# Это безопаснее, чем git pull, потому что не меняет твои файлы
git fetch origin

# Создать локальную ветку на основе удалённой
# После этой команды ты окажешься в новой ветке, которая отслеживает удалённую
git checkout -b <имя_локальной_ветки> origin/<имя_удалённой_ветки>

# Посмотреть историю коммитов конкретной ветки (даже если ты в другой ветке)
# Это полезно, чтобы понять, что сделал коллега, не переключаясь в его ветку
git log origin/<имя_ветки> --oneline -n 10

# Посмотреть, чем отличается твоя ветка от чужой
# Показывает коммиты, которые есть в одной ветке, но нет в другой
git log origin/main..HEAD

# Сравнить содержимое двух веток (какие файлы отличаются)
git diff origin/main...HEAD

# Удалить локальную ветку после того, как она слилась
# -d = --delete (безопасное удаление, только если ветка слита)
# -D = принудительное удаление (даже если не слита)
git branch -d <имя_ветки>
```

## 🎓 Правила сдачи заданий

1. Каждое задание выполняется в **отдельной ветке**, созданной от твоей базовой ветки `feature/<твой_ник>`.
2. После выполнения задачи всегда создавай **Pull Request** (кроме заданий, где указано создать Issue).
3. В описании Pull Request кратко напиши, что было сделано. Если задача связана с Issue, напиши `Closes #<номер_задачи>`, чтобы GitHub закрыл её автоматически при слиянии.
4. Никогда не делай `push` изменений напрямую в ветку `main`!
5. **Никогда не используй `git push --force` в общих ветках** (`main`, `develop`). Только в своих личных ветках `feature/<твой_ник>/...`.
